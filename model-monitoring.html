Model Monitoring Tool

A monitoring and governance product scoped and shipped to a Tier-1 U.S. bank, now tracking 380+ models in production. Here are four of its workflows, walked through with a fictional bank and made-up data.

Role
Product owner, end to end
Context
Tier-1 U.S. bank, Corridor Platforms
Scale
380+ models tracked in production
Built
Dashboard · Alerts · MCP assistant · Insights to deck

7 min read

The problem

Banks run hundreds of models in production and have to keep proving, continuously, that each one is still doing what it's supposed to. Past a handful of models, nobody can do that by hand.

The approach

One connected surface instead of four separate tools: a dashboard people can reconfigure themselves, alerts that catch problems automatically, an assistant that answers questions in place, and a faster way to turn a report into a deck.

How we judged it

Could a model owner find what changed, get told about it before it became a problem, and explain it to someone else, without waiting on us to pull a report?

Real client details, screens and data are confidential. Everything below uses a fictional bank, Northwind Decisions, and made-up numbers. The prototypes are illustrative: they show how the workflows work, not a one-to-one replica of what shipped.

Framing

The dashboard was never the hard part

A table of models with their status is easy to build. What's hard is that every bank's governance policy is slightly different: different fields matter, different roles need different levels of access, and the definitions themselves (what counts as "overdue," what a given metric even means) are something each bank has already decided and won't change for us.

So the dashboard had to be configurable by the people using it, not just by us. That one requirement is what turned a reporting screen into a small platform of its own, with its own permissions, its own change history, and its own validation so a bad edit doesn't quietly reach real data.

Flow 1 · Monitoring dashboard

Configurable without filing a ticket

Admins can add a column, change what a field means, or edit the logic behind a metric themselves. Analysts get the same dashboard as a clean, read-only view. Every change is validated and logged before it touches real data.

Flow 2 · Alert email builder

A dashboard only helps if someone looks at it

Alerts close that gap. When a condition is met, like a review date going overdue, the platform sends an email automatically instead of waiting for someone to notice. The part I spent the most time on is the body editor: it supports variables that pull in real values, and it validates them before you can save, so a typo doesn't silently break a notification someone is relying on.

Flow 3 · Platform assistant over MCP

Answers inside the tool people already have open

This one follows on from the agent connectors work: once the platform's data was reachable over MCP, the natural next step was an assistant that could answer questions about it directly, instead of sending someone off to go find a report. It has to do three things well: give a real answer when there is one, admit it when a search comes up empty, and decline gracefully when asked to do something it isn't allowed to do, like approving a model on someone's behalf. Server instructions also let an admin teach it the bank's own vocabulary, so "AMR" means Annual Model Review without anyone explaining that twice.

Flow 4 · Insights to presentation

From report to deck without starting over

Portfolio reviews end in a deck. For a long time, getting from "here's what changed this month" to something a committee could actually sit through meant a few hours of someone copying numbers into slides by hand. This flow collapses that: generate an insight on a report, turn it into a draft presentation, edit it like a normal slide, and present straight from the same screen. Rerunning the analysis flags anything that's gone stale, so a deck doesn't quietly fall out of date.

Outcome

What's live, and what's still a prototype

The dashboard and the monitoring core behind it are live, tracking 380+ models in production for the bank it was built for. Alerts, the assistant and the presentation flow are the next layer: scoped and prototyped, shown here as working click-throughs rather than confirmed, shipped features.

What I'd want to validate next

  • Who actually opens an alert email. Sending a notification is easy. Knowing whether it changed what someone did that day is the real test.
  • Where the assistant should stop. It's deliberately narrow right now. The interesting question is which of the things it declines today are worth building properly.
  • Whether a draft deck is actually faster. Editing a generated slide might still take as long as building one from scratch. Worth timing against the old way before calling it a win.

Takeaway

Governance tooling is a configuration problem

The lesson that carried across all four flows: the hard part is almost never the feature itself. A table, an email, a chat window and a slide editor are all well-understood pieces of software. The hard part is that every bank already has its own policy, its own vocabulary and its own idea of who gets to touch what. Building for one bank is building a feature. Building for a platform means building the places where each bank can make it theirs.
