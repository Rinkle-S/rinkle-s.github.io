Autonomous Agent Connectors

An MCP server and a Claude Code plugin that let an AI agent read and write credit-risk policies on our platform, plus the domain-knowledge layer that keeps its reasoning inside the rules.

Role
Led a 3-person team
Context
Internal hackathon, Corridor Platforms
Result
1st place · ₹1L prize pool
Built
MCP server · Claude Code plugin · skills layer

6 min read

The problem

Credit-risk policy work is slow and expert-heavy. Analysing a policy, testing a change and comparing simulation runs means moving between screens and carrying a lot of context in your head.

The bet

An agent could do the legwork, if it could actually reach the platform, and if it knew enough about credit risk not to confidently get it wrong.

How we judged it

Could an analyst ask for a policy analysis in plain language and get back something they'd be willing to act on, with the reasoning visible?

This was an internal hackathon project. Platform specifics, screenshots and client data are left out on purpose. This write-up is about the product decisions, not the implementation.

Framing

"Give the agent our APIs" was the easy half

When the hackathon was announced, the obvious pitch was a chatbot over our platform. We spent the first hours arguing ourselves out of it. A chat window would have demoed well and been useless on Monday: the work our analysts do isn't one question and one answer, it's a loop of read, change, simulate, compare.

So we reframed the goal. Not "a bot that answers questions about policies," but "an agent that can sit inside the policy workflow and do a chunk of it." That reframe is what produced three pieces of work instead of one, and, I think, what won the thing.

Three gaps between an LLM and a useful teammate

GapWhat it looks likeWhat we built
Reach The model can reason about a policy you paste in, but can't fetch one, change one, or run a simulation. An MCP server exposing platform APIs as agent tools: read and write, across policies and simulation data.
Judgement It knows "credit risk" generically, so it fills gaps with plausible-sounding assumptions that don't hold here. A domain-knowledge layer of bundled skills that constrains reasoning to our credit-risk context.
Fit A separate chat tab is one more place to go, so it doesn't get used. A Claude Code plugin, so the entry point is the terminal the team already has open.

How it fits together

One path in, one set of rules

The analyst drives the agent from Claude Code. Every platform action goes through the MCP server, there's no second route in, and the knowledge layer travels with the agent, shaping how it reasons before it ever calls a tool.

The decisions that mattered

Three calls I'd make again

1 · Write access, scoped deliberately

Read-only was the safe option and we rejected it. An agent that can only describe a policy saves a few minutes of reading; an agent that can draft a change and run the simulation against it changes what the job looks like. The risk isn't write access itself. It's unreviewed write access.

So the MCP server became the only door. One surface to scope, one place where every action is visible, and a human in the loop on anything that counts. Designing the tool boundary turned out to be the actual product work: each tool had to be narrow enough to reason about and useful enough to be worth calling.

2 · A knowledge layer, not a longer prompt

Our first attempts failed in the most believable way: the agent produced credit-risk analysis that read correctly and quietly assumed things that aren't true on our platform. Stuffing more context into the prompt made it worse and slower.

I owned this piece, and the fix was structural. Instead of one big instruction blob, we bundled the domain into discrete skills: definitions, how policies are structured, and explicitly what the agent must not assume, so the relevant slice loads when it's relevant. Constraining the agent did more for output quality than any amount of encouraging it.

3 · Meet people where they already are

Shipping as a Claude Code plugin rather than a new interface meant no new tool to learn, no new login, and no separate tab to remember. For a three-day build it also meant we spent our time on the connectors and the domain layer instead of on a front end that would have been thrown away.

Outcome

What we shipped, and what's next

We placed 1st out of the internal field, against a ₹1L prize pool, with a working end-to-end path: a plain-language request in Claude Code, resolved through MCP tools into real reads and writes on the platform, with the agent's reasoning grounded in our own domain skills.

  • An MCP server exposing platform APIs for agent read and write access across policies and simulation data.
  • A Claude Code plugin with commands for credit-risk policy analysis and optimisation.
  • A domain-knowledge layer of bundled skills constraining the agent's reasoning to credit-risk context.

What I'd do next

  • Evaluate it properly. A hackathon demo proves the path works, not that the output is reliable. The next step is a graded set of real policy tasks with expert-reviewed answers, so "better" becomes a number instead of a vibe.
  • Make review a first-class step. Right now a human checks the agent's writes because they're watching. That belongs in the product: a diff to approve, not a log to read.
  • Find out who it's actually for. It was built for analysts like the ones I work with daily. Whether it helps a new joiner more than an expert is an open and interesting question.

Takeaway

Agent products are scoping problems

I went in expecting the challenge to be model quality. It wasn't. Nearly every decision that mattered was a product decision in disguise: which actions to expose, how narrow to make each one, what the agent is allowed to assume, and where a human has to stay in the loop.

That's the same work as any other product: pick the surface, define the boundary, and be honest about what you haven't validated yet. The model is just a new kind of component on the other side of it.
